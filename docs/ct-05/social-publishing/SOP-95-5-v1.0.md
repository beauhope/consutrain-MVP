# ConsuTrain — CT-05 | Social Publishing Automation 95/5
**SOP:** CT-05-SP-SOP-001 · **Version:** v1.0 (Working Baseline) · **Date:** 2026-10-20 · **Status:** Partially verified / NOT production-approved.

> This operational record mirrors the Arabic Word SOP. The workflow is not yet fully production-ready; the Facebook 403 issue remains unresolved. Never store credentials or page access tokens in this repository.

## 1. Operating principle (95/5)
**Human (~5% target):** In Google Sheet `Content_Library`, select the article, set `Approved=TRUE`, and set `LinkedIn_Status=Ready` and/or `Facebook_Status=Ready`.

**Automation (~95% target):** `Content_Library → Queue Builder → Publish_Queue → [LinkedIn Queue Reader | Facebook Publisher] → API → Publish_Log + Content_Library`. The goal is no second human approval in `Publish_Queue`. The percentage is a design target, not an achieved measurement.

## 2. System and scope
- ConsuTrain.com Arabic/French articles: legacy JSON, standalone HTML and Tech Radar.
- Google Sheets: `ConsuTrain – Social Publishing Hub`, with `Content_Library`, `Publish_Queue`, `Publish_Log`.
- n8n locally hosted on a Windows laptop; scheduled runs stop if PC/n8n/internet is unavailable.
- LinkedIn destination: Youssef Joul. Facebook destination: ConsuTrain page (page ID `108117601461105`).
- Out of scope: YouTube, paid advertising and website article publishing.

## 3. Governance / invariants
1. `Approved + Ready` in the source library is the sole human approval gate.
2. Deduplicate by `Content_ID + Channel`, and avoid parallel processing / duplicate social posts.
3. `Published` only after an API-confirmed post ID/URN; uncertain responses require manual verification before any retry.
4. A `Failed` row must not be blindly reset to `Ready` without checking the platform for existing publication.
5. No access tokens or secrets in the repository, document or spreadsheet.
6. Do not activate old/backup and new scheduled publisher workflows simultaneously.
7. Prefer existing current workflow JSON exports, backed up before any changes.

## 5. Queue Builder runbook
1. Schedule trigger is intended every 5 minutes. Do not enable until integration acceptance.
2. Read `Content_Library` approved entries and existing `Publish_Queue`.
3. Select the first eligible article in sheet order; support independent LinkedIn and Facebook per selected article.
4. Extract source body (legacy article JSON, standalone HTML or Tech Radar HTML).
5. Build AR/FR platform-specific social copy, validate required fields, avoid duplicate `Content_ID|Channel`.
6. Append candidate with `Queue_ID`, `Status=Ready`, `Ready_To_Publish=TRUE`, `Publish_Now=TRUE`.
7. Stop without side effects if no eligible article.

## 6. LinkedIn Queue Reader runbook
- Filter: `Status=Ready`, `Channel=LinkedIn`, `Target_Account=Youssef Joul`.
- Order: `Get row(s) → If [six authorization/identity checks] → Limit (1, first) → Edit Fields → Update row in sheet (Publishing) → Create a post`.

- On error or missing identifier: failure/verification pathway, with no blind repost.

## 7. Facebook Publisher runbook
- Read Facebook rows gated by `Status=Ready`, `Ready_To_Publish=TRUE`, `Publish_Now=TRUE`, `Target_Account=ConsuTrain`.
- Safety gate requires nonempty Queue ID, Content ID and Social Text; single eligible item per execution.
- Lock one item and mark `Publishing` before API dispatch.
- Check image candidate; publish a photo if valid, otherwise a text post.
- Update `Published` and records only when API returns validated post ID. For uncertain outcomes use `Verification Required`.
- Mock test `TEST-FB-001` returned `Safety_Check=PASSED` (remove pinned test data before production).
- **Blocked:** two live calls to `Create Facebook Text Post` returned `403 / OAuthException #200` relating to page posting permissions.

## 8. Troubleshooting: Facebook HTTP 403 / #200
- A green `Connection tested successfully` only establishes credential connectivity; it does not establish permission to publish.
- Meta Access Token Debugger showed a valid **Page** token for ConsuTrain, with `pages_show_list`, `pages_read_engagement`, `pages_manage_posts`; despite that, API calls were rejected.
- Next action: check actual page task `CREATE_CONTENT` / sufficient Page access, current app mode and app/page authorization, and verify Page ID matches target. For diagnosis, on Graph API Explorer with page token call `GET /me?fields=id,name,tasks` (do not paste token in chats).
- Investigate Facebook app permissions and token lifespan; debugger showed token expires in about an hour at observation. Fix long-term token strategy before 95/5 operation.
- Do not keep regenerating tokens or repeating live posts without narrowing the cause.

## 9. Status transitions
| Status | Meaning | Rule |
|---|---|---|
| Ready | Authorized, generated, queued | Dispatch at most once |
| Publishing | Claimed / in-flight | No concurrent dispatch |
| Published | Platform-confirmed post | Store URI, date, clear switches |
| Failed | Explicit API rejection | Record error, no blind retry |
| Verification Required | Ambiguous after request | Inspect platform before retry |
| Pending Review | Legacy/manual draft | Not eligible under 95/5 until consciously migrated |
